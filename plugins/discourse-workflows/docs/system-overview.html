⚡ Discourse Workflows

System Architecture

Discourse Workflows is a visual automation engine. Workflows are graphs of trigger, condition, action, and flow nodes connected by directed edges. Items (JSON objects) flow through the graph.

Core Concepts

📊
Items
The unit of data flowing through the graph. Each item is {"json": {...}}. Nodes receive arrays of items and return arrays of items — one input fan can produce many outputs.
🔀
Connections
Directed edges between node output ports and node input ports. A node can have multiple output ports (e.g., IF node has true and false outputs). Items flow only through matching ports.
🧠
Execution Context
Tracks which nodes have run, their outputs, trigger data, current user, sandbox state. Persisted as JSON in ExecutionData and referenced during resumption.
= { }
Expressions
Any parameter value starting with = is a live JavaScript expression evaluated in a MiniRacer sandbox. ${"$"}{json.topic_id}, ${"$"}("Fetch Topic").first().json.title…
📸
Workflow Snapshot
When an execution starts, the current workflow structure (nodes + connections) is snapshotted. Long-running executions (with wait nodes) use the snapshot so mid-flight edits don't corrupt them.
🔒
Credentials
Encrypted API credentials (basic auth, bearer tokens) stored separately from workflows. Referenced by credential_id in HTTP request nodes, injected at runtime.

Node Category Colors

Triggers — start a workflow in response to an event
Conditions — branch or filter the item stream
Actions — perform side-effects, produce output
Flow — transform, loop, split, sort, limit items

Node Types

35 node types across four categories. Every node is versioned (v1.rb, v2.rb…) so old executions keep working when behaviour changes.

🔀 Conditions

Condition nodes split the item stream. Items go down the true or false output port based on evaluation.

condition
if
Evaluates one or more condition rules per item. Uses and / or combinator.

Operators: equals, not_equals, greater_than, less_than, contains, not_contains, is_empty, is_not_empty, regex.

Output ports: true and false.
condition
filter
Similar to if but designed for collections. Items that pass flow to the true port; rejected items flow to false.

Useful when working with loop_over_items or list_topics — filter down before performing actions.

🎬 Actions

Action nodes perform side-effects. They receive items, do something (create a post, call an API…), and produce output items containing the result.

flow

Queries Discourse topics by filter, category, tags, etc. Returns multiple items — one per topic.
flow
data_table
Reads from or writes to a persistent in-DB data table. Enables workflows to accumulate state across executions.

Execution Engine

The executor is a queue-based graph traversal. It processes nodes in topological order, threading items between them, and handles waiting, errors, and branching.

Execution Algorithm

1. Claim & Snapshot
The executor locks the workflow execution row. If resuming (after a wait), the saved WorkflowSnapshot is rehydrated — guaranteeing structural consistency even if the admin edited the workflow mid-flight.
2. Seed Queue
The trigger node is enqueued with its trigger data as the initial item: [{ "json": { ...trigger_data } }].
3. Process Queue
Pop next (node_id, items) from queue. Find node type in registry. Resolve all configuration expressions against current items. Call node.execute(context).
4. Route Output
Node returns Array<Array<Item>> — one item array per output port by index. For each downstream connection, enqueue the destination node with the matching output index's items.
5. Wait (optional)
If a node raises WaitRequested, the execution is paused: status=waiting, waiting node + resume_token saved. The Sidekiq job finishes but the execution is not complete.
6. Complete / Fail
When queue empties → finish!. On unhandled exception → fail! (saves error + triggers error workflow if configured). Sandbox is always disposed in ensure.
def execute_flow
  start_execution!     # or resume_execution!
  process_queue
  finish!
rescue WaitRequested => e
  begin_wait!(e.waiting_until)
rescue => e
  @store.fail!(error: e, steps: @steps)
ensure
  @sandbox&.dispose
end

def process_queue
  while (entry = @queue.shift)
    node_id, items = entry
    execute_node(node_id, items)
  end
end

def execute_node(node_id, items)
  node     = @snapshot.find_node(node_id)
  context  = NodeExecutionContext.new(...)
  result   = node_type.execute(context)
  record_step!(node, result)
  enqueue_downstream!(node, result)
end
Iteration guard: The executor tracks total iterations and aborts at 1,000 to prevent infinite loops. This guards against badly-wired graphs (e.g., cycles via data_table writes).
Parallelism: The queue is processed sequentially in a single Sidekiq job. There is no concurrent node execution — the graph is topologically ordered and each step is atomic.

Step Statuses

success — node ran, output produced
error — node raised an exception
waiting — node paused execution (form, wait node)
filtered — condition node sent item to false port
running — node is currently executing
skipped — node type unavailable or issues detected

Resume Flow (Wait Nodes)

1
Node raises WaitRequested
The form or wait node calls raise WaitRequested.new(waiting_until: time). The executor's rescue block catches it.
2
Execution paused
execution.status = "waiting". resume_token (UUID) and waiting_until saved. All steps so far persisted in execution_data.
3
External signal arrives
Form submission or inbound webhook POST to /workflows/waiting/:execution_id/webhook/:suffix?signature=SIGNATURE.
4
Claim for resume
execution.claim_for_resume() atomically sets status back to running. Returns false if already claimed (prevents double-resume).
5
Executor.resume()
A new Sidekiq job calls Executor.new(...).resume(execution, response_items). The snapshot is rehydrated, queue starts from the node after the wait point.

Expression Engine

Any parameter value can be a live JavaScript expression evaluated in an isolated MiniRacer (V8) sandbox. Expressions give you full access to the current item, previous node outputs, trigger data, and Discourse context.

Syntax Forms

= expression
The entire value is replaced by the expression result. If the expression returns an object, you get an object.
// Returns the topic title as a string
= $json.topic.title

// Returns an integer
= $json.post.word_count * 2

// Access a previous node's output
= $("Fetch Topic").first().json.category_id
= text {{ expr }} text
String template: the value is a string with {"{{ }}"} interpolation blocks. Each block is independently evaluated and coerced to string.
// "Post #42 in topic: My Title"
= Post #{{$json.post.post_number}} in topic: {{$json.topic.title}}

// Combine static and dynamic parts
= Hello {{$json.user.name}}, welcome!

Available Variables

Sandbox Architecture

Each execution gets a single MiniRacer (V8) context. The context is created once, pre-loaded with all node outputs, trigger data, and variables — then individual expression evaluations call into that shared context.

Timeout: 30ms per expression evaluation. Exceeded → expression returns null, error logged.
Memory cap: 10 MB per sandbox.
Max injected JSON: 1 MB total.
Sandbox disposal: Always called in the executor's ensure block. Prevents V8 memory leaks even on crashes. 
# lib/discourse_workflows/js_sandbox.rb
class JsSandbox
  TIMEOUT_MS = 30
  MAX_MEMORY = 10 * 1024 * 1024

  def evaluate(expression)
    @ctx.eval(expression, timeout: TIMEOUT_MS)
  rescue MiniRacer::ScriptTerminatedError
    log_error("timeout")
    nil
  end

  def dispose
    @ctx&.dispose
  end
end

Expression Error Classification

:undefined
Reference to a variable or property that doesn't exist. Silent — returns null without failing the execution. E.g., $json.nonexistent_field
:invalid
Syntax error or runtime exception. Logged in the step's expression_errors array but execution continues with a null value.

Webhook System

Webhooks serve three distinct purposes: triggering workflows from external services, resuming paused executions, and sending responses back to callers.

1. Webhook Trigger

URL format: /workflows/webhooks/:path?token=:secret — the path and token are auto-generated when you add a webhook trigger node.
1
Inbound HTTP request
Any HTTP method. Body can be JSON or form-encoded. Token validated via HMAC. Rate limit: 20 req/10s per IP.
2
WebhookRequestParser
Parses body (JSON or form). Strips sensitive headers (Authorization, Cookie). Max body: 1 MB. Returns { body, headers, query, method }.
3
WorkflowDependency lookup
Finds all published workflows whose trigger node matches this webhook path. Multiple workflows can share a webhook endpoint.
4
ExecuteWorkflow job enqueued
One Sidekiq job per matching workflow. The webhook payload becomes the trigger item.
5
Response
If the workflow contains a respond_to_webhook node, its output is used as the HTTP response. Otherwise a 200 OK is returned immediately (async execution).

2. Resume Webhook (Wait / Form)

URL format: /workflows/waiting/:execution_id/webhook/:suffix?signature=:signature
This URL is available as $execution.resume_url in expressions — you can embed it in emails, posts, or forms.
1
POST to resume URL
External agent (user clicking a link, form submission) sends a request with the signed resume URL.
2
Signature validation
Signature must validate against execution.resume_token. Execution must be in waiting status and not past waiting_until.
3
Atomic claim
execution.claim_for_resume() uses a database-level update with WHERE status = 'waiting' to prevent double-resume races.
4
Resume job enqueued
Sidekiq job calls Executor#resume(execution, response_items). Execution continues from the node after the wait point.

Respond to Webhook Node

response_body: = { status: "ok" }

# Default response output item

never_error: By default, 4xx/5xx HTTP responses fail the step. Set never_error: true and full_response: true to treat all responses as success and inspect $json.statusCode yourself in a downstream IF node.
Response size limit: Max max_response_size_kb (default 1024 KB). Responses exceeding this are truncated with an error flag in the output.
Credentials: Stored encrypted in the DiscourseWorkflows::Credential model. Never exposed in expressions or logs. Injected at request-build time by Authenticator.

Condition Evaluation

The if and filter nodes evaluate a set of condition rules against each item. Items are partitioned into true/false output ports.

Condition Rule Structure

{
  "combinator": "and",   // "and" = ALL rules must pass  |  "or" = ANY rule must pass
  "conditions": [
    {
      "left":     "= $json.topic.category_id",  // expression: left-hand value
      "operator": "equals",                   // comparison operation
      "right":    "5"                          // literal or expression
    },
    {
      "left":     "= $json.post.word_count",
      "operator": "greater_than",
      "right":    "100"
    }
  ]
}

# lib/discourse_workflows/nodes/if/v1.rb
def execute(context)
  true_items  = []
  false_items = []

  context.items.each do |item|
    result = evaluate_conditions(
      context.configuration[:conditions],
      context.configuration[:combinator],
      item
    )
    result ? true_items << item
           : false_items << item
  end

  [true_items, false_items]
end
Both ports always get items — items that don't match go to false, not dropped. To drop items entirely, leave the false port unconnected or use the filter node.

Common Patterns

Category-based routing ▶ 
// Route support posts to Slack, other posts to a different action
{
  combinator: "and",
  conditions: [{
    left: "= $json.topic.category_id",
    operator: "equals",
    right: "= $site_settings.support_category_id"  // right can also be an expression
  }]
}
Multi-condition with OR ▶ 
// True if post has "urgent" tag OR word_count > 500
{
  combinator: "or",
  conditions: [
    { left: "= $json.topic.tags", operator: "contains", right: "urgent" },
    { left: "= $json.post.word_count", operator: "greater_than", right: "500" }
  ]
}

Error Handling

Errors are handled at three levels: individual expression errors (silent, logged), individual step errors (recorded, halt propagation), and workflow-level failures (trigger error workflow).

Error Propagation Layers

Level 1: Expression Error
A JavaScript expression fails (syntax error, undefined reference, timeout). Silent — the expression returns null. Errors are appended to the step's expression_errors array. Execution continues with the null value substituted.
Level 2: Node Step Error
The node's execute() method raises an exception. Step status is set to error. Downstream nodes are not enqueued — the branch dies here. Other branches in the workflow continue normally (errors are per-branch, not global).
Level 3: Execution Failure
The executor's top-level rescue catches any unhandled exception. store.fail!(error: e, steps: @steps) is called. Execution status → error. If an error workflow is configured, it's triggered.
Level 4: Error Workflow
A separate workflow designated as the error handler. Called with the failed execution's data as its trigger payload. Runs in execution_mode: error_mode to prevent infinite error loops (error workflows cannot themselves trigger error workflows).

Execution Failure States

error
Execution Failed
An exception was raised and not caught by any node. The execution record has status="error" and the error column contains the exception message + backtrace summary.
waiting
Paused (Not an Error)
Execution is suspended at a wait or form node. Not an error condition — will resume when triggered. Has a waiting_until deadline and a resume_token.
rate_limited
Rate Limited
Webhook trigger hit the 20 req/10s limit. The inbound request is rejected with 429. No execution record is created.
skipped
Skipped
Workflow is disabled, or a node type doesn't exist in the registry (plugin removed mid-execution). The entire execution skips cleanly.
timeout
Wait Timeout
An execution that was waiting exceeded waiting_until. A scheduled job calls execution.fail_with_timeout!(). Optional timeout_action parameter controls the fallback path.
loop guard
Max Iterations
The executor aborts after 1,000 queue iterations. This protects against cycles created by data_table write → read → write patterns.

HTTP Request Error Handling

# Default: 4xx/5xx fail the step
never_error: false  ← default

# With never_error: true and full_response: true — inspect status manually
IF node:
  left:     "= $json.statusCode"
  operator: "greater_than"
  right:    "399"
  → true branch handles the error
  → false branch continues on success
No automatic retry. Failed HTTP requests are not retried by the executor. Build retry logic explicitly with a loop or re-trigger mechanism if needed.
Credential errors (bad token, credential not found) fail the step immediately with a descriptive error message referencing the credential ID.

Node Issues Pre-flight Check

Before executing a node, NodeIssues validates its configuration. If critical issues are found, the step is marked skipped with a reason — the node never executes. This catches things like missing required parameters, invalid node types, or incompatible input shapes before they cause runtime errors.

Form System

Forms pause workflow execution, display a UI to a user, then resume with the submission data. Two modes: an inline form action node (mid-workflow) and a standalone form_trigger (entry point).

Two Form Modes

action:form
Mid-workflow Form
A form that appears during an already-running workflow. The execution pauses (status=waiting) and a form URL is generated using $execution.resume_url. When submitted, the execution resumes from the node after the form.

Typical use: approval flows, collecting additional data mid-process.
trigger:form_trigger
Standalone Form Entry
A public form URL that starts a new workflow execution. No pre-existing execution context. The form submission becomes the trigger payload.

Typical use: contact forms, intake questionnaires, event registrations.

{
  page_type:           "single" | "multi",
  form_title:          "= \"Request: \" + $json.topic.title",
  form_description:    "Please fill in the details below.",
  form_fields: [
    { type: "text",     name: "requestor_name", label: "Your name",    required: true },

Form Resume Flow

1
Form node executes
Node renders form configuration as JSON. Raises WaitRequested. Execution pauses. resume_url is embedded in the form's HTML via template.
2
User sees form
Form served from /public/form-workflow/ — a standalone static page. Reads form config from the execution's waiting data. No Discourse login required (public forms).
3
Form submitted
POST to $execution.resume_url with form fields as JSON body. WebhookRequestParser extracts the body.
4
Execution resumes
Form submission data becomes new items available as $json in the next node. Original trigger data still accessible via trigger variable.

Encrypted API credentials. Fields: name, type (basic_auth/bearer_token), data (encrypted JSONB). Referenced by credential_id in HTTP request nodes.

Variable

Read-only key-value store. Accessible as $vars.KEY in expressions. Scoped per-workflow or global.

Persistent tabular storage. Each table has a schema (columns + types). Workflows can read/write rows across executions — enables stateful automation.

Index table: maps trigger type+key to workflow IDs. Used for fast lookup: "which workflows listen to event X?" Rebuilt when workflows are saved.
